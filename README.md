# Alloca

### Give Every Peso a Purpose

A personal finance application built around a **student's weekly allowance cycle** rather than a
salaried worker's monthly budget. Alloca assumes cash, manual entry, and small purchases that
would otherwise go unrecorded — the ₱40 jeep fare and the ₱85 canteen lunch that quietly empty an
allowance three days before it resets.

```
Set allowance → Receive allowance → Spend → Log expenses → Monitor balance
     → Receive alerts → Finish cycle → Review surplus → Improve next cycle
```

## What it does

| Feature | Detail |
| --- | --- |
| **Quick expense logging** | Category → amount → save. Three taps in the normal flow; the note is optional and never blocks a save. Reachable from the dashboard button or the raised **+** in the mobile navigation bar. |
| **Real-time dashboard** | Weekly allowance, total spent, remaining balance, percentage remaining, daily spending rate, days remaining, spending health, recent transactions and a category breakdown. |
| **Automatic weekly reset** | Defaults to **Monday at 12:00 AM**; the day and time are both configurable. Cycles roll forward on their own and history is never destroyed. |
| **Savings goals** | Target, current amount, deadline, contributions, progress and a projected completion date based on the average weekly surplus — with honest messaging when no projection is possible. |
| **Reports** | Weekly and monthly reports, category breakdowns, spending trends, cycle comparisons and a weekly surplus history table, all drawn from real transactions. |
| **Spending alerts** | `SAFE` / `WATCH` / `AT_RISK`, with an estimate of how many days early the allowance will run out at the current pace. |
| **Extra income** | Gifts, side jobs, freelancing and reimbursements are added to the cycle's pot and shown distinctly from expenses. |
| **Category management** | Six student defaults (Meals, Transport, Projects, Leisure, School, Other) plus custom ones. Categories with history are hidden, never deleted. |

## Tech stack

| Layer | Choice | Why |
| --- | --- | --- |
| Framework | **Next.js 15** (App Router, React 19) | Server components render the dashboard's numbers in the first paint; route handlers give a clean API layer in the same project. |
| Language | **TypeScript** (strict) | Every module is typed, including the enum-like string columns. |
| Styling | **Tailwind CSS 3** + design tokens | One palette defined as CSS variables in `app/globals.css`; light and dark both derive from it. |
| Components | Hand-built primitives on **Radix UI** (shadcn/ui conventions) | Accessible dialog, select, tabs, switch and progress behaviour without shipping a component framework. |
| ORM | **Drizzle ORM** | Fully typed schema and queries in TypeScript, with SQL migrations generated by `drizzle-kit`. |
| Database | **SQLite** in development (`better-sqlite3`) | Runs with zero external services. PostgreSQL is a two-file change — see [Database](#database). |
| Auth | **Custom JWT sessions** (`jose` + `bcryptjs`) | Password hashing with bcrypt, sessions signed with HS256 and stored in an httpOnly cookie. |
| Charts | **Recharts** | Real transaction data; no placeholder series anywhere. |
| Data fetching | **SWR** | Server-rendered payloads are handed to SWR as `fallbackData`, so lists are populated on first paint and only refetch after a mutation. |
| Validation | **Zod** | One schema per concern in `lib/validation/`, used by both the API routes and the forms. |
| Tests | **Vitest** (unit + integration) and **Playwright** (end-to-end) | 144 unit/integration tests and an e2e suite covering the main flow on desktop and mobile viewports. |

> **A note on the ORM.** The brief suggested Prisma; Drizzle was chosen instead because it needs no
> downloaded query-engine binary, which keeps `npm install` self-contained and lets the whole test
> suite run anywhere. The separation of concerns is identical: schema in `db/schema.ts`, migrations
> in `db/migrations/`, seed in `db/seed.ts`, and no query outside `services/`.

## Architecture

Alloca is layered, and each layer only talks to the one below it:

```
app/                 pages (server components) and route handlers
   │
components/          presentational + small client components
   │
hooks/               client-side data fetching and mutations (SWR)
   │
services/            all database access, scoped by userId
   │
lib/calculations/    pure financial functions — no I/O, fully unit tested
lib/validation/      Zod schemas shared by API and forms
   │
db/                  schema, migrations, seed
```

Two rules hold everywhere:

**1. No financial arithmetic inside a component.** Components call named functions:

```ts
// components/dashboard/remaining-balance-card.tsx
const health = calculateSpendingHealth(snapshot.percentageRemaining, snapshot.cycleProgress)
```

not

```tsx
const remaining = allowance + income - expenses.reduce(...)   // never
```

Every calculation lives in its own module: `balance.ts`, `spending-risk.ts`,
`savings-projection.ts`, `budget-cycle.ts`, `reset-date.ts`, `weekly-surplus.ts`,
`transaction-total.ts`, `report-calculations.ts`.

**2. No query without a user id.** Services take a `userId` obtained from the verified session
cookie and filter every query on it. There is no code path where a client-supplied id reaches the
database.

## Getting started

**Requirements:** Node.js 20 or newer, and npm.

```bash
# 1. install dependencies
npm install

# 2. create your environment file
cp .env.example .env
#    then set AUTH_SECRET — generate one with:
#    openssl rand -base64 32

# 3. create the database and fill it with demo data
npm run db:migrate
npm run db:seed

# 4. start the app
npm run dev
```

Open <http://localhost:3000> and sign in with the seeded account:

```
email     demo@alloca.app
password  allowance123
```

Or click **Get started** to register a fresh account — new accounts get the six default categories
and their first allowance cycle immediately.

## Database

Six entities, joined by foreign keys rather than stuffed into one JSON blob:

```
User ─┬─< Category ──< Transaction >── BudgetCycle
      ├─< BudgetCycle
      ├─< Transaction
      └─< SavingsGoal ──< SavingsContribution
```

| Table | Notes |
| --- | --- |
| `users` | Credentials, allowance, reset schedule, currency, notification preferences. |
| `categories` | Per-user. `is_hidden` rather than deletion once a category has history. |
| `budget_cycles` | One row per allowance week. Closed cycles freeze their totals so later profile edits cannot rewrite history. |
| `transactions` | Expenses and income share the table; `type` decides the sign in every calculation. Amounts are always stored positive. |
| `savings_goals` | `current_amount` is kept in step with its contributions inside a single database transaction. |
| `savings_contributions` | Every deposit into a goal, with a date and an optional note. |

**Moving to PostgreSQL:** change `dialect` in `drizzle.config.ts` to `'postgresql'`, swap the two
driver imports in `lib/database/client.ts` for `postgres` / `drizzle-orm/postgres-js`, point
`DATABASE_URL` at your server, and regenerate migrations. The schema, services, calculations and UI
are untouched.

### Seed data

`npm run db:seed` builds a realistic demo account: **seven allowance cycles** (six completed, one in
progress) at ₱1,500 a week, roughly 180 small cash transactions across all six categories, three
pieces of extra income, and two savings goals — one in progress (₱2,175 of ₱8,000 toward a drawing
tablet) and one already funded. The randomness is seeded, so the numbers are identical on every run.

## Testing

```bash
npm test          # 144 unit + integration tests
npm run test:e2e  # 3 end-to-end journeys × 2 viewports
```

**Unit tests** cover the pure financial functions, including the awkward cases: a cycle with no
transactions, an overspent allowance, day one of a cycle (no division by zero), a savings goal with
no history, a zero surplus, a negative surplus, a deadline already passed, and a custom reset day
and time.

**Integration tests** run against a real SQLite database created from `db/migrations` in a temporary
directory — one per test file, so nothing leaks between them. They exercise the service layer
directly: recording expenses and income, the effect on the remaining balance, category
hide-versus-delete, savings contributions and completion, and the weekly reset (a back-dated cycle
is closed, its totals frozen, a new one opened, and its transactions left untouched). They also
assert that one account can never read or modify another's data.

**End-to-end tests** drive a real browser through register → dashboard → log an expense → watch the
balance fall → create a savings goal → open the reports, plus the redirect for signed-out visitors
and the rejection of bad credentials. They run on a desktop viewport and a Pixel 7 viewport.

If your environment already has a Chromium build on disk, set `PLAYWRIGHT_CHROMIUM_PATH` to point at
it; otherwise `npx playwright install chromium` downloads one.

## Production build

```bash
npm run build
npm run start
```

Before deploying, set `AUTH_SECRET` to a strong random value, point `DATABASE_URL` at a persistent
database, and run `npm run db:migrate` against it. Session cookies are automatically marked
`secure` when `NODE_ENV=production`.

**Performance.** The dashboard is a server component that makes one round trip and loads only the
current cycle's rows, never the whole transaction history. There is no client-side loading waterfall
on first paint. Fonts are a system stack, so no webfont request blocks rendering. Recharts is loaded
only on the reports route. Measured first-load JS: ~148 kB for the dashboard, ~102 kB shared.

## How the core logic works

### The weekly reset

There is no cron job. Cycles roll forward **lazily**: whenever the app asks for "the current cycle"
(`services/budget-service.ts → ensureCurrentCycle`), it checks whether the active cycle has expired.
If it has, the cycle is closed — its income, expenses and surplus frozen onto the row — and a new
one is opened covering the present moment. A student who does not open the app for three weeks still
gets intact history rather than one giant cycle, and **old transactions are never deleted**.

The boundaries themselves come from two pure functions in `lib/calculations/reset-date.ts`:

```ts
calculateCycleStart(reference, settings)  // most recent reset at or before `reference`
calculateNextReset(reference, settings)   // the instant the current cycle closes
```

Dates advance with `setDate`, not by adding milliseconds, so a cycle spanning a daylight-saving
change still starts at the chosen wall-clock time.

### Balance and pace

```
available  = allowance + income
remaining  = available − expenses
dailyRate  = expenses ÷ days elapsed        (days elapsed floored at 1)
safeDaily  = remaining ÷ days remaining
```

### Spending risk

`calculateSpendingRisk` projects the current pace to the end of the cycle:

```
projectedSpend   = spent + dailyRate × daysRemaining
projectedBalance = available − projectedSpend
```

* `AT_RISK` — the projection ends below zero, or the money is already gone.
* `WATCH` — the projection ends above zero but below 10% of the pot.
* `SAFE` — anything else.

The message names the shortfall in days: *"At your current spending rate, your allowance may run out
2 days before your next reset. Keeping to ₱193.27 a day gets you there."*

### Weekly surplus

```
Allowance + Cycle Income − Cycle Expenses = Surplus
```

Shown per cycle in the reports table as **Week | Allowance | Income | Spent | Surplus | Savings rate**,
with a running total driving the "Running surplus" chart.

### Savings projections

The average surplus of the last eight completed cycles is the funding assumption. Each awkward case
gets its own state rather than a misleading date:

| State | When |
| --- | --- |
| `COMPLETED` | The target is already met. |
| `NO_HISTORY` | No cycle has closed yet, so there is nothing to project from. |
| `NO_SURPLUS` | The recent average is zero or negative. |
| `ON_TRACK` | The projection lands on or before the deadline (or there is no deadline). |
| `AT_RISK` | It lands up to two weeks late — the message says what per-cycle amount would close the gap. |
| `BEHIND` | It lands more than two weeks late, or the deadline has already passed. |

## Security model

* **Passwords** are hashed with bcrypt (cost 10) and never leave `lib/auth/password.ts`. No response
  anywhere in the app includes a password hash — `lib/database/mappers.ts` is the only place a user
  row becomes JSON, and it maps to `PublicUser`.
* **Sessions** are HS256 JWTs in an `httpOnly`, `sameSite=lax` cookie, marked `secure` in
  production. Client JavaScript cannot read the token.
* **Authorization** is checked three times over: `middleware.ts` guards the routes at the edge,
  `requireSession()` / `requireUserId()` guard the render and every route handler, and each service
  query filters on the session's `userId`. A request for another account's record returns 404, not
  that account's data.
* **Validation** happens server-side with Zod on every write. The forms use the same schemas, but the
  server never trusts them.
* **Login responses** are deliberately identical for an unknown email and a wrong password, and the
  handler hashes a dummy value when the email is unknown so timing does not reveal it either.

## Accessibility

* Semantic landmarks (`header`, `nav`, `main`, `section`) and a skip link to `#main`.
* Every input has a real `<label>`; errors are wired with `aria-describedby` and `role="alert"`.
* The category picker is a proper `radiogroup`; navigation marks the current page with
  `aria-current`.
* Touch targets are at least 44 px tall; the mobile **Add** button is 56 px.
* Focus is always visible (`:focus-visible` ring on every interactive element).
* Charts sit beside the same numbers in text, and the surplus table has a caption and row headers.
* `prefers-reduced-motion` disables animation; colour is never the only signal (badges carry text).

## Deliberate limitations

Alloca does **not** integrate with banks, GCash, credit cards or any financial API. Everything is
entered by hand, and that is the point: automated tools only see the transactions that leave a
digital trail, which is exactly the wrong half of a cash-spending student's week.
